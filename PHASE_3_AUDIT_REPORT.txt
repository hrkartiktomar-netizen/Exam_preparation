================================================================================
FEATURE BREAKDOWN
================================================================================

1. ADAPTIVE MOCK ALLOCATION (60/25/15)
   • Weak topics: 60% of total questions (focused remediation)
   • Medium topics: 25% of total questions (confidence + challenge mix)
   • Strong topics: 15% of total questions (easy - confidence building)
   • Ranking: Based on user_accuracy descending
   • Allocation accuracy: ±2% tolerance for integer rounding

2. DIFFICULTY PROGRESSION
   • Weak topics: Scaffolded as easy → medium → hard (pedagogical)
   • Medium topics: Mixed easy + hard (confidence + challenge)
   • Strong topics: All easy (confidence building)
   • Per-question control: difficulty_curve[topic] = ["easy", "medium", "hard", ...]
   • Rationale: Helps students gradually tackle weak areas

3. SERVER-SIDE TIMER ENFORCEMENT
   • Exam duration: 3600 seconds (60 minutes)
   • Calculation: elapsed = (now - started_at).total_seconds()
   • Submit validation: Returns 403 EXAM_TIME_EXPIRED if elapsed > 3600
   • Security: Prevents client-side bypass (e.g., tampering with localStorage time)
   • Polling: Frontend polls every 5 seconds for live time display

4. TCS iON EXAM UI
   • Question palette: 50-cell grid (5 rows × 10 columns)
   • Cell states: ■ (answered), □ (unanswered), ★ (marked), ★■ (answered+marked)
   • Navigation: Back/Forward at question level, direct jump to any question
   • Marking for review: Toggle flag, updates palette cell state
   • Negative marking display: "+4 for correct, -1 for wrong, 0 for unanswered"

5. SCORING + WEAK AREA DETECTION
   • Positive marking: +4 per correct, -1 per wrong, 0 per unanswered
   • Score calculation: (correct × 4) + (wrong × -1) + (unanswered × 0)
   • Weak area ID: Topics with accuracy_pct < 60%
   • Per-topic breakdown: correct/total → accuracy_pct for each topic

6. STATE PERSISTENCE
   • Storage: localStorage (browser-native persistence)
   • Auto-save: On each user action (answer selection, marking, navigation)
   • Recovery: On page refresh or browser close/reopen
   • Clear: After successful exam submit

================================================================================
ARCHITECTURE DECISIONS
================================================================================

1. Exam Mode (Session-Only, No DB Persistence)
   Rationale: Phase 3 v1 focuses on UI/UX. Phase 4+ could add exam history
   Impact: No exam records stored (student can save screenshot if needed)
   Future: Add exam_history table with full submission audit trail

2. Server-Side Timer (Not Client-Side)
   Rationale: Prevent time manipulation attacks
   Implementation: elapsed = (now - started_at).total_seconds()
   Security: 403 EXAM_TIME_EXPIRED if elapsed > 3600 on submit
   Fallback: If server clock skew > ±60s, consider adding tolerance

3. Difficulty Curve as List (Not Single Value)
   Rationale: Enable per-question difficulty within topic
   Enables: Pedagogical scaffolding (easy→hard progression)
   Trade-off: Slightly more complex data structure, but worth it

4. localStorage for Persistence (Not IndexedDB)
   Rationale: Simpler API, sufficient for single exam session
   Limitation: ~5-10MB limit (not an issue for 50-question exam)
   Future: Consider IndexedDB for multi-session history

================================================================================
RISK MITIGATION
================================================================================

1. Client-Side Timer Spoofing
   → Fixed: Server calculates elapsed time, any submission > 3600 gets 403
   → Frontend timer is UI-only (cosmetic countdown)

2. localStorage Clear on Browser Close
   → Handled: Auto-save on each action
   → User recovers state on browser reopen (same device)

3. Question Allocation Rounding Errors
   → Fixed: Tolerance ±2% to account for 60% of 50 = 30.0 exact, 25% of 50 = 12.5 ≈ 12/13
   → Verified: All allocation tests validate accuracy

4. Answer Data Loss
   → Mitigated: Every answer selection auto-saved to localStorage
   → Auto-submit when time expires (no manual submit needed if user forgets)

5. Question Shuffling Determinism
   → Addressed: Questions shuffled after generation (random order)
   → Each exam session gets unique random order
   → No localStorage of shuffled order (doesn't matter for single use)
